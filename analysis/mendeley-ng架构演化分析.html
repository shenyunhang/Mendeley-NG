f864926｜八个布尔标志 → 一个带 payload 的 View 联合类型

git show f864926:src/lib/view.ts（节选）
/**
 * The middle of the window used to be decided by a chain of eight
 * ternaries — `adding ? … : importing ? … : ftMode ? …` — each one a
 * separate piece of state that happened to be non-null. That is modes
 * piled on top of each other, not a view: nothing says what is on screen
 * now, only what was turned on last …
 * A screen that is not showing is not merely hidden, it does not exist.
 */
export type View =
  | { kind: 'library' } | { kind: 'fulltext' }
  | { kind: 'import'; entries: Entry[] } | { kind: 'add' }
  | { kind: 'dupes'; groups: DupeGroup[] }
  | { kind: 'trash'; docs: Doc[] }
  | { kind: 'annotations'; anns: Annotation[] }
范式切换的本质从「状态 = 若干独立标志」变成「状态 = 一个代数数据类型」：payload 随视图走，视图不显示时数据就不存在，从类型层面消除了 stale 副本。后续 ba89d99（reading 成为独立 View）、c0d575c（viewAfterReadingToggle）都是同一范式延伸。

6结论

这 18 天不是「从零写了一个应用」，而是「把一个已经能跑的单体，沿着『磁盘事实可信 / 跨进程输入不可信 / 异步结果需要归属标记』三条约束，一层层剥成可验证的结构」。三次范式切换各自解决一类不可靠性：入口拆包解决职责不可辨，View 联合类型解决状态不可信，单测地基解决改动不可验。

遗留的演化断点（已被主动登记）HANDOFF.md:682-698：App.tsx 剩余状态簇、smoke.ts 剩余的 UI 驱动链、fulltext.ts 索引状态机仍主要靠源码串断言守护、五份 JSON 无 schema 版本。它们是「下一轮」的起点，而不是遗漏。
重构后记（2026-11-16）本轮重构继续了第 5.2 节描述的「一份规则被逐步吸走所有调用点」模式：把剩余四个检索 UI、七个脚本的公共底座与两份 workflow 的产物校验接回共享实现，并为每次抽规则补上逐值差分测试。详见 analysis/优化重构说明.md。
